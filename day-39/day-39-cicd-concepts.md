# Day 39 - CI/CD Concepts

## Objective
Understand CI/CD purpose, pipeline anatomy, and real-world usage.

## Task 1 - The Problem
- Risks of manual deployment: Inconsistent environments, missed steps, hotfix conflicts, long downtime, and hard-to-trace failures.
- Meaning of "works on my machine": Code runs in a developer local setup but fails elsewhere due to dependency, config, or environment differences.
- Manual safe deploy frequency: Usually low and risk-heavy; most teams cannot safely deploy many times per day without automation.

## Task 2 - CI vs CD
- Continuous Integration: Developers frequently merge code into shared branches; automated builds and tests validate changes early.
- Continuous Delivery: Every change that passes CI is packaged and ready for release, but production release is still a business/manual decision.
- Continuous Deployment: Every change that passes the full pipeline is automatically deployed to production.
- Real-world example for each:
	- CI: Run lint, unit tests, and build on each pull request.
	- Continuous Delivery: Deploy automatically to staging and keep a release-ready artifact for manual production approval.
	- Continuous Deployment: A SaaS service auto-deploys each successful main branch merge.

## Task 3 - Pipeline Anatomy
- Trigger: The event that starts the pipeline, such as push, pull_request, schedule, or manual dispatch.
- Stage: A logical phase in delivery flow, such as build, test, security scan, or deploy.
- Job: A collection of steps executed on one runner; jobs can run sequentially or in parallel.
- Step: A single command or reusable action inside a job.
- Runner: The machine (hosted or self-hosted) that executes workflow jobs.
- Artifact: Files generated by a job and stored for later use, such as binaries, reports, or logs.

## Task 5 - Open Source Workflow Study
- Repo explored: actions/starter-workflows
- Workflow file: ci/node.js.yml (example workflow)
- Trigger: push and pull_request
- Number of jobs: Typically one main job with matrix variations
- What it does: Sets up Node.js, installs dependencies, runs tests/build checks to validate code changes.

## Learnings
1. CI/CD reduces deployment risk by converting manual steps into repeatable automation.
2. Fast feedback from CI prevents broken code from propagating to shared branches.
3. Delivery maturity grows from CI to Delivery to Deployment based on team risk tolerance and confidence.
